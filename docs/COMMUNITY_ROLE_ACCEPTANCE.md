# 社區管理：角色流程驗收

本次以 Well101 的隔離資料副本驗證。測試帳號、住戶姓名、信件、通行碼及截圖保留在私有驗收資料夾，不放入公開倉庫。通知只驗證 Odoo 郵件佇列、收件人及正文，未向正式住戶寄送測試信。

## 管理室與住戶應如何使用

1. 管理室建立管理室、戶號，將住戶聯絡人加入戶號；確認住戶標記、Email，透過 Odoo 原生「授予入口網站存取權」邀請住戶。
2. 收件後登記快遞條碼、戶號及物品，通知有效住戶。住戶從「社區管理 → 包裹」查詢。交付前由管理室核對戶號、物品及身分，再確認取件。
3. 沒有 Email 的住戶仍可現場領取；現場交付記錄實際操作人員與時間，不將未寄出的信件標成已寄送。
4. 臨時訪客由警衛登記並送出確認；住戶在入口網站或通知連結確認／拒絕。警衛確認入場、離場，系統管理訪客證的借用與歸還。
5. 預約訪客由住戶建立通行單，依畫面顯示時區填寫時間。警衛輸入／掃描通行碼核驗，通過後記錄入場；同一訪客尚未離場時不可重複核驗入場。
6. 住戶可提交寄放物品或意見反映；錯誤時保留輸入，管理室接收、處理與結案。

## 原生功能的取捨

| 功能 | 實作與界線 |
|---|---|
| QR 圖片 | 沿用 Odoo `ir.actions.report.barcode`，未加入第三方 QR 服務。 |
| 通行碼 | 保留既有代碼與資料相容性；業務規則仍檢查有效時間、次數、黑名單、操作角色。產生 QR 本身不代表有權放行。 |
| 快遞條碼 | 使用原生欄位及搜尋，支援鍵盤式掃描器輸入；條碼只查件，不代表取件人身分。 |
| 確認交付 | 原生按鈕確認、ORM 權限及 Chatter 狀態記錄，不另造匿名領件入口。 |
| 通知 | 原生 `mail.template`、QWeb 與郵件佇列；已通知表示成功排入佇列，不保證外部 Email 已送達。 |
| 日期時區 | 使用 Odoo 日期與格式化能力，儲存 UTC、顯示使用者時區；不回溯平移舊預約時間。 |
| 住戶入口 | 原生 Portal、登入、CSRF 與 record rules；跨戶資料保持隔離。 |

## 驗收矩陣

- 管理者：後台選單、收件通知、現場交付、寄物接收／完成、公告與意見處理。
- 住戶：桌面／手機入口、待領包裹、訪客確認／拒絕、預約、寄物、意見表單。
- 負面情境：無戶號、無 Email、空白／非法日期、跨戶 ID、已領件重領、通行碼重播、逾時、黑名單。
- 競態：同一通行碼同時核驗、同一訪客證同時發放。
- 升級：原版本資料副本升級、保留自訂郵件文字與 QWeb 屬性、保留舊通行碼與既有日期。

## 本輪實際結果（2026-11-11）

- 在 Well101 資料副本完成管理者、住戶及無關住戶的真實 HTTP／Chromium 操作。
- 包裹通知／查看／取件、訪客確認／入場／離場、住戶預約／原生 QR／查驗視窗、寄物及意見結案：全部通過。
- 五種跨戶明細隔離、390px 手機六種入口／表單無橫向溢出：通過；完整流程未捕獲未處理 JavaScript 錯誤。
- 兩個獨立 HTTP session 同時使用單次通行碼：僅一次成功、僅一筆訪問；同時發放同張訪客證：僅一人取得。
- 舊版住戶回報測試：4 項中 2 項失敗，可重現原問題。新版完整回歸 50 項全部通過（0 failed、0 errors）。
- 升級已以原版郵件範本與版本資訊排演，保留自訂 QWeb 屬性；舊預約未猜測住戶時區或平移日期。

## 界線與發布

- 通知驗到收件人、正文及原生郵件佇列，未實際投遞 Email；未使用實體掃描器／手機相機，鍵盤式代碼輸入與原生 QR 產圖已驗證。
- 一併修正兩個預約套件日曆註冊名稱衝突；社區管理者沒有預約管理權限，因此未宣稱已操作兩套預約日曆的 New 功能。
- 單進程測試服務曾因併行瀏覽器超過 8 個資料庫連線出現 pool full；最終完整角色流程通過。正式服務的連線設定未修改。
- 本報告對應原始碼候選版，尚不代表正式 Well101 已部署本輪修補。須經 PaaS 映像管線與租戶升級驗收。
- repository 根目錄與 `addons/` 的三個模組副本維持相同，現行 PaaS 來源路徑可繼續使用。
